# Архитектура

## Границы

`apps/mobile` сохраняет слои domain/data/features. Domain описывает правила приложения, data реализует репозитории, features использует TanStack Query и контекст репозиториев. Точка композиции — `src/data/appRepositories.ts`. Только каталог переключается переменными `mock|api`; ошибки API не заменяются демонстрационными данными.

`apps/api/src/modules` содержит функциональные модули каталога и health. Prisma, модель хранения, миграции и seed принадлежат API. CatalogService преобразует модель БД в публичный DTO и валидирует ответ через `@sbg/contracts`; Prisma-модели не экспортируются в mobile.

`packages/contracts` содержит публичные DTO и схемы валидации. Node использует собранный JavaScript, Metro — условие react-native. Пакет не импортирует NestJS, Prisma, React Native или Node API. Идентификаторы изображений остаются стабильными: mobile сопоставляет их с прежними локальными assets, поэтому URL файлов и доступ к серверному storage не нужны.

## Данные на телефоне

AsyncStorage сохраняет прежние ключи `sbg-coffee:cart:v1`, `sbg-coffee:profile:v1`, `sbg-coffee:orders:v1`, `sbg-coffee:favorites:v1`. Перенос директорий не меняет Android package / iOS bundle ID `com.sbgcoffee.app` и scheme `sbgcoffee`. Пользовательские данные не очищаются. SQLite не вводится.

Каталог отдельно сохраняется в AsyncStorage вместе со временем получения. Это явная персистентность поверх TanStack Query: кеш в памяти сам по себе не переживает перезапуск. Кеш разделяется по источнику и API URL, проверяется перед использованием и служит для просмотра без сети. Данные из кеша и время обновления показываются пользователю; цена из кеша не считается подтверждённой сервером. Повторный запрос и ошибка доступны даже при наличии сохранённого каталога. Никакого зеркалирования всей PostgreSQL на телефон нет.

## Данные на сервере

PostgreSQL — источник актуальных товаров, вариантов, объёмов и цен каталога. Цены хранятся целыми тенге, а не float. Seed восстанавливает исходное меню для локальной разработки и интеграционных проверок; повторный запуск не создаёт дубликаты. Seed явно запрещён при `NODE_ENV=production` и не входит в deployment. Для рабочего каталога нужен отдельный проверенный процесс импорта/администрирования. Повторный development-seed перезаписывает цены исходных товаров, поэтому не предназначен для рабочей БД.

Полное рабочее меню и правила его импорта описаны в [menu.md](menu.md). Новые Dessert/DessertVariant и Addon добавлены отдельно от прежних таблиц напитков: старый Prisma и API продолжают читать Product/ProductVariant после наполнения. `GET /api/v2/catalog/products` возвращает также штучные товары и добавки. Mobile использует v2 и отдельный кеш каталога; старые корзины/заказы читаются с пустым набором добавок.

`GET /health` проверяет подключение к БД. `GET /api/v1/catalog/products` читает данные БД; при её недоступности возвращает ошибку. Каталог read-only; никаких endpoints заказов или авторизации этот этап не добавляет.

## Что остаётся демонстрацией

Профиль локальный и не является учётной записью. Заказы создаются локальным адаптером с `isDemo: true`; это не подтверждение принятия кофейней. Самовывоз и оплата на кассе остаются демонстрационным сценарием. Карта лояльности не начисляет реальные бонусы. Переключение каталога на API не меняет эти границы и не включает платежи/POS.

## Будущие заказы, аккаунты и лояльность

Будущий `POST /api/v1/orders` принимает идентификаторы товаров/вариантов, количества и Idempotency-Key. Сервер проверяет пользователя, доступность и действующие цены в транзакции, возвращает итоговую стоимость и собственный ID/статус. При расхождении цен требуется явное подтверждение нового предложения. Клиент не присылает доверенный итог и не устанавливает статус «принят» самостоятельно.

Ключ идемпотентности хранится на сервере с ограничением уникальности для пользователя/операции и хешем тела. Повтор того же запроса возвращает тот же заказ, а другой payload с тем же ключом — конфликт. Повтор после обрыва связи сначала выясняет статус принятия, не создавая новый заказ.

Разрешённые переходы статусов проверяет сервер с учётом роли. Журнал лояльности — серверные неизменяемые проводки с уникальным событием основания; начисления связаны с подтверждённым выполнением/оплатой, отмены — с компенсирующей проводкой. Клиент не начисляет бонусы. Интеграции оплаты/POS требуют отдельных адаптеров, подписанных webhook и повторяемой обработки событий.

Токены будущей авторизации хранятся в защищённом системном хранилище (например, SecureStore), не в AsyncStorage. `EXPO_PUBLIC_*` встраивается в клиент и публично: туда допустим URL API, но не DATABASE_URL, SSH/GHCR токены и другие серверные секреты.

## Эволюция и доставка

Mobile и API имеют независимые циклы выпуска. Изменения v1 должны быть обратно совместимыми; новые обязательные поля/изменение семантики требуют новой версии или переходного периода. Миграции выполняются из того же Docker-релиза перед переключением API и должны поддерживать работающую предыдущую версию (expand → migrate/backfill → contract отдельным выпуском). Откат контейнера не откатывает схему БД. Один API-контейнер может дать кратковременный простой при обновлении.
